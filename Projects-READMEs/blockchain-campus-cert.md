# 基于区块链的校园学生信息与学业资料防篡改存证方案

> 面向高校信息化建设的联盟链存证解决方案 —— 让学业资料的真实性不再依赖任何单一环节的自觉

## 项目简介

高校学生学籍信息与学业资料具有**终身有效性、多方参与、高频使用**三大特征，但传统"集中式数据库 + 纸质证明 + 公章"模式在真实性保障上存在结构性缺陷。

本方案基于 **FISCO BCOS 联盟链**，采用"**链上存哈希、链下存原文**"混合架构，实现学业资料的**真实性可验证、变更可追溯、核验可自助、隐私可保护**。

### 核心特性

| 特性 | 实现方式 | 效果 |
|------|----------|------|
| 防篡改 | SM3 哈希指纹上链 | 内容改动一位，验真立即失败 |
| 可追溯 | 版本历史只追加、无删除接口 | 任意时点状态可还原，不可抵赖 |
| 可核验 | 公开验真接口 + 二维码 | 核验耗时从"数天"降至"秒级" |
| 隐私保护 | 明文不上链，仅存哈希 | 满足《个人信息保护法》要求 |
| 多方互信 | 四方节点分权共识 | 单方作恶无法改变链上数据 |

## 在线演示

直接用浏览器打开 [`demo/index.html`](demo/index.html) 即可运行，无需任何环境依赖。

演示包含 5 个标签页，完整覆盖业务闭环：

1. **资料存证** —— 录入资料 → 计算 SM3 哈希 → 机构 SM2 签名 → 合约调用 → 共识出块
2. **验真核验** —— 上传文件比对链上指纹，一键「模拟篡改」直观验证防篡改能力
3. **变更追溯** —— 资料更新与撤销，查看完整版本历史链
4. **链上浏览** —— 区块视图与链上存证记录表
5. **节点状态** —— 四方联盟链节点运行状态

> **推荐体验路径**：进入「验真核验」页 → 点击「模拟篡改后验真」→ 观察系统如何识别内容改动。

### 编译智能合约

**Solidity 版（Remix / Hardhat）**

1. 打开 [Remix IDE](https://remix.ethereum.org/)
2. 新建文件，粘贴 `contracts/solidity/CampusCertRegistry.sol`
3. 编译器选择 `0.8.19` 及以上，点击 Compile
4. 部署后即可调用存证与验真接口

**FISCO BCOS 版（WeBASE / Console）**

```bash
# 使用 FISCO BCOS Console 部署
cp contracts/fisco/CampusCertRegistry_FISCO.sol ~/fisco/console/contracts/solidity/
cd ~/fisco/console

# 编译（Solidity 0.4.25）
./console.sh
[group:1]> deploy CampusCertRegistryFISCO
```

## 技术架构

### 四层架构

```
┌─────────────────────────────────────────────────────────────┐
│  应用层   教务管理端 │ 学生自助端 │ 第三方验真门户 │ 审计监管端  │
├─────────────────────────────────────────────────────────────┤
│  服务层   存证服务 │ 验真服务 │ 证书签发 │ 权限与身份服务(CA)   │
├─────────────────────────────────────────────────────────────┤
│  区块链层  FISCO BCOS 联盟链                                 │
│           共识节点×4 │ 存证合约 │ 白名单合约 │ 访问控制合约   │
├─────────────────────────────────────────────────────────────┤
│  存储层   学生信息系统DB │ 对象存储(原文) │ 校内存证库(密文)   │
└─────────────────────────────────────────────────────────────┘
```

### 联盟链节点规划

| 节点 | 归属机构 | 职责 | 权限 |
|------|---------|------|------|
| Node-A | 教务处 | 成绩单、学籍信息存证 | 存证机构 |
| Node-B | 研究生院 / 学院 | 学位、综合素质档案存证 | 存证机构 |
| Node-C | 信息化中心 | 链运维、合约管理 | 管理员 |
| Node-D | 学信中心 / 监管部门 | 独立见证、审计 | 只读审计 |

> 四方分属不同权力主体，需超过 2/3 共识才能出块，任何单方无法作恶。

### 存证数据流

```
原始资料（PDF/图片）
      │  SM3 哈希运算
      ▼
  数据指纹 dataHash  ──────────►  上链存储（不可篡改）
      │
      ▼
  资料原文  ────SM4 加密────►  链下存储（校内对象存储）
```

**上链数据**：materialId、studentHash（学号哈希）、dataHash、时间戳、机构地址
**不上链数据**：姓名、身份证号、成绩明细等一切敏感明文

## 智能合约接口

| 接口 | 类型 | 权限 | 功能 |
|------|------|------|------|
| `registerMaterial` | 写 | 白名单机构 | 登记新资料存证 |
| `updateMaterial` | 写 | 白名单机构 | 更新资料（版本+1） |
| `revokeMaterial` | 写 | 白名单机构 | 撤销资料（留痕） |
| `batchRegister` | 写 | 白名单机构 | 批量存证（Merkle 根上链） |
| `verify` | 读 | 公开 | 哈希比对验真 |
| `getMaterial` | 读 | 公开 | 查询资料详情 |
| `getHistory` | 读 | 公开 | 查询版本历史 |
| `checkOwnership` | 读 | 公开 | 校验资料归属 |
| `setIssuer` | 写 | 管理员 | 机构白名单管理 |

### 验真结果四态判定

| 结果 | 触发条件 | 系统提示 |
|------|---------|---------|
| 验真通过 | 哈希一致且状态有效 | 该资料真实有效，未被篡改 |
| 内容被篡改 | 哈希不一致 | 验真失败，文件内容已被篡改 |
| 资料已撤销 | 哈希一致但状态为已撤销 | 该资料已被撤销，请谨慎采信 |
| 未找到记录 | 链上无此编号 | 链上未找到该资料存证记录 |

## 关键设计决策

### 1. 为什么链上只存哈希，不存明文？

区块链全节点数据公开可查。若将成绩、身份证号直接上链，等同于公开泄露。而哈希函数具有**单向性**，链上仅保存指纹即可完成防篡改校验，原文留在校内合规存储中，兼顾**可信**与**隐私**。

### 2. 为什么要四方节点而非单校自建？

单一主体自建链等于既当运动员又当裁判，防篡改意义大打折扣。四方节点分属不同权力主体，形成相互制衡。

### 3. 版本历史为什么只增不删？

合约中不存在任何 `delete` 操作。资料变更只追加新版本记录，旧版本归档但不删除。任何持有旧版资料的第三方仍可验证其"曾经真实存在过"，但会被告知已被新版取代。

### 4. 系统故障时为什么宁可返回"无法验证"也不返回"验证失败"？

验真结果只有四种：一致且有效、哈希不一致、已撤销、不存在。系统超时或异常时若返回"验证失败"，会被核验方误读为"这份资料是假的"，造成实际损害。因此容错设计的第一原则是：**永远不返回错误结论**。

## 方案能力边界（诚实说明）

区块链存证**并非万能**，以下场景仍需管理制度配合：

| 边界场景 | 说明 | 配套措施 |
|---------|------|---------|
| **源头造假** | 若资料在上链前就录入错误，区块链只能证明"数据从某时点起未变"，**不能证明数据本身正确** | 录入双人复核制度 |
| **私钥泄露** | 机构私钥被盗则攻击者可冒名写入 | HSM 硬件加密机保管私钥 |
| **链下原文丢失** | 存储损坏且无备份时，哈希还在但无法还原原文 | 异地容灾备份 |
| **量子计算威胁** | 远期签名算法可能被破解 | 关注抗量子签名算法演进 |

> 明确能力边界是技术方案严谨性的体现，而非缺陷。

## 合规性

| 法规 | 相关要求 | 本方案应对 |
|------|---------|-----------|
| 《个人信息保护法》 | 最小必要、敏感信息保护 | 敏感明文不上链，仅存哈希 |
| 《数据安全法》 | 数据分类分级保护 | 数据分层存储，链上链下分离 |
| 《网络安全法》 | 等保合规 | 国产联盟链，支持等保三级 |
| 《电子签名法》 | 可靠电子签名法律效力 | SM2 数字签名 |
| 教育行业信创要求 | 国产自主可控 | FISCO BCOS + 国密算法全栈 |
